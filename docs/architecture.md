# Architecture
FastAPI + psycopg (raw SQL, transactions per request) + PostgreSQL. JWT (8h) + bcrypt. Patient access is allowed for a linked facility, or another facility with current `CLINICAL`/`ALL` consent recorded by the patient's linked hospital. Cross-facility consent is facility-scoped, includes purpose and a documentation reference, and can expire or be revoked. Search returns only linked patients and patients with current consent; knowing an Arovia ID alone does not expose a patient. Allowed and denied patient access and consent actions are recorded in `access_logs`. Referral creation requires current consent for the receiving facility. Referral status and its history are written in the same transaction while locking the referral row. Directory listing, verification and participation are separate facility fields. Images are stored under uploads/ with sha256 and metadata in retinal_images.

Supported login roles are Super Admin, Hospital Admin, Doctor, and Optometrist. Hospital Admins register patients and manage facility clinical records; Doctors can add and review clinical records and create referrals; Optometrists retain retinal screening and image capture workflows. Migration 006 converts legacy Registration Staff accounts to inactive Hospital Admin accounts for review before reactivation.

Patient registration captures identity and contact details only and creates no clinical encounter. Medical history, allergies, diagnoses, prescriptions, investigations, procedures, treatment, and notes are added through separately recorded clinical work; encounter-associated records reference the encounter. History items and allergies distinguish patient-reported information from clinician-recorded information. Encounters and their records retain source facility and provider provenance. New encounters are appended and earlier records are preserved. Investigation report references are metadata only; report file upload is not implemented.

The retinal flow is upload -> quality gate -> AI result -> clinician review. Grades >=2 display a specialist referral prompt; a doctor must create and send the referral, and the target facility must have consent. This is clinical decision support, not an autonomous diagnosis or auto-referral. Prediction returns 503 until a model is available.

# Remaining limitations
Application document upload, charts, migrations tooling, automated tests, and dedicated follow-up task records are not implemented. Referral status history supports notes for follow-up actions, but does not yet schedule or assign follow-up tasks.

# Retinal pipeline (v2)
Upload -> quality gate (app/quality.py: resolution, field coverage, brightness, contrast, sharpness; thresholds via Q_* env vars, heuristic, validate on your images) -> if rejected: status REJECTED_QUALITY, no prediction, no review -> if accepted: POST /screenings/{id}/predict runs the configured model (app/inference.py, MODEL_PATH) -> doctor review. Run database migrations 002, 003, and 004 in order on existing databases.
